# Deploying RAAS-OCJS on a GCP VM — Step-by-Step Operator Guide

This guide walks an operator from **a bare Google account with no billing set up** all the
way to **a verified, running judge that promotes a memory-heavy submission live**. Every
step is derived from what is actually committed under [`deploy/`](../deploy/README.md:1) —
nothing here requires a code change to the repository.

The deployment is a **single Compute Engine VM running a native Docker daemon with the
judge as root**. That shape is a hard requirement, not a preference: the judge writes
`memory.high` into the host cgroup v2 tree and drives the Docker socket to spawn sibling
containers. Serverless platforms (Cloud Run, Cloud Functions, App Engine, GKE Autopilot)
withhold one or both, so they cannot host it. See
[`deploy/README.md`](../deploy/README.md:6) for the full rationale.

## 1. What you are going to build

| Component | What it is | Source |
| --- | --- | --- |
| One GCE VM | `e2-standard-4` (4 vCPU / 16 GiB), Ubuntu 24.04 LTS, 30 GiB `pd-balanced` | [`variables.tf`](../deploy/terraform/variables.tf:28) |
| Dedicated VPC | Default-deny ingress; only IAP on `tcp/22` opens by default | [`main.tf`](../deploy/terraform/main.tf:50) |
| Docker daemon | Pinned to the `systemd` cgroup driver | [`startup.sh.tftpl`](../deploy/terraform/startup.sh.tftpl:53) |
| Three runtime images | `python-judge-runtime`, `cpp-judge-runtime`, `java-judge-runtime`, built locally | [`startup.sh.tftpl`](../deploy/terraform/startup.sh.tftpl:104) |
| Rust judge service | Installed as a `systemd` unit **but left stopped** until a secret exists | [`startup.sh.tftpl`](../deploy/terraform/startup.sh.tftpl:149) |
| Shared secret | Generated by `deploy.sh` into `/etc/raas/judge.env`, never through Terraform | [`deploy.sh`](../deploy/deploy.sh:100) |

The only APIs the configuration enables are **Compute Engine** and **Identity-Aware Proxy**
([`main.tf`](../deploy/terraform/main.tf:30)). No GKE, no Cloud Run, no Artifact Registry.

> **Security reality check.** `/submit` compiles and executes arbitrary submitted source.
> The default posture leaves `tcp/3000` with **no firewall rule at all**, so the service is
> unreachable from the internet even though it binds `0.0.0.0:3000`. Do not open it unless
> you deliberately set `judge_source_ranges` to a single narrow CIDR.

## 2. Prerequisites and local tooling

You need the following on **your own machine** (the one you deploy from):

- A Google account.
- `gcloud` CLI.
- Terraform (`>= 1.5`, per [`main.tf`](../deploy/terraform/main.tf:12)).
- `git`, `python3` (used by [`deploy.sh`](../deploy/deploy.sh:163) to shape the smoke-test
  payload), and `openssl` (generates the shared token).
- A local clone of this repository.

### 2.1 Install the Google Cloud SDK (gcloud)

The reference environment installs it into `~/google-cloud-sdk` without `sudo`
([`deploy/README.md`](../deploy/README.md:62)). On a Debian/Ubuntu host:

```bash
cd "$HOME"
curl -O https://dl.google.com/dl/cloudsdk/channels/rapid/downloads/google-cloud-cli-linux-x86_64.tar.gz
tar -xf google-cloud-cli-linux-x86_64.tar.gz
./google-cloud-sdk/install.sh --quiet
exec -l "$SHELL"          # reload PATH
gcloud version
```

Alternatively install it system-wide following Google's official repository instructions,
or use `snap install google-cloud-cli --classic`.

### 2.2 Install Terraform

Install into `~/.local/bin` (the layout the repo assumes) or any directory on `PATH`:

```bash
mkdir -p "$HOME/.local/bin"
cd "$HOME/.local/bin"
TERRAFORM_VERSION=1.9.8
curl -O "https://releases.hashicorp.com/terraform/${TERRAFORM_VERSION}/terraform_${TERRAFORM_VERSION}_linux_amd64.zip"
unzip -o "terraform_${TERRAFORM_VERSION}_linux_amd64.zip"
rm "terraform_${TERRAFORM_VERSION}_linux_amd64.zip"
export PATH="$HOME/.local/bin:$PATH"     # add to ~/.zshrc to persist
terraform version
```

> `unzip` must be installed (`sudo apt-get install -y unzip` on Debian/Ubuntu).

### 2.3 Clone this repository

```bash
git clone https://github.com/Hemanthkumar2k04/RAAS-OCJS.git
cd RAAS-OCJS
```

If you are already working inside the project directory, skip the clone.

## 3. Set up GCP login and billing

If you already have a project with billing enabled and the Compute Engine API usable,
skip to [§4](#4-authenticate-gcloud-and-terraform).

### 3.1 Create the Google Cloud account

1. Open <https://console.cloud.google.com/>.
2. Sign in with your Google account.
3. Accept the Terms of Service. New accounts are typically offered a **90-day, USD 300
   free trial** credit — this deployment costs a few dollars at most, so the trial covers
   it many times over.

### 3.2 Create a project

Console → **Select a project → New Project**.

| Field | Suggested value |
| --- | --- |
| Project name | `RAAS-OCJS` |
| Project ID | `raas-ocjs` (must be globally unique — append digits if taken) |
| Organization | your default / none |
| Location | your organisation |

Note the **Project ID** exactly; it is used verbatim in `terraform.tfvars`.

CLI equivalent:

```bash
gcloud projects create raas-ocjs --name="RAAS-OCJS"
```

### 3.3 Enable billing on the project

Billing must be enabled or `terraform apply` fails when it tries to create the VM.

**Console:** Billing → **Link a billing account** → create one if needed (name, country,
currency, payment method) → link it to the project.

**CLI:**

```bash
# List billing accounts you can use
gcloud billing accounts list

# Link the chosen account to the project
gcloud billing projects link raas-ocjs \
  --billing-account=0X0X0X-0X0X0X-0X0X0X
```

> **India note.** Charges are billed in **INR** and attract **18% GST**. The reference
> figure is roughly **Rs 0.19/hr** for `e2-standard-4` in `asia-south1`
> ([`deploy/README.md`](../deploy/README.md:107)). Verify current rates in the
> [GCP pricing calculator](https://cloud.google.com/products/calculator) before budgeting.

### 3.4 (Optional) Verify quota

`e2-standard-4` needs **4 E2 vCPUs**. New projects sometimes cap E2 vCPUs below that.
Check:

```bash
gcloud compute regions describe asia-south1 \
  --project=raas-ocjs --format='value(quotas)'
```

If `CPUS_PER_VM_FAMILY` or the regional CPU quota is below 4, request an increase, or drop
to `e2-standard-2` for a smoke test by overriding `machine_type` in `terraform.tfvars`
([`deploy/README.md`](../deploy/README.md:157)).

You do **not** need to enable the Compute Engine API by hand — Terraform enables
`compute.googleapis.com` and `iap.googleapis.com` itself
([`main.tf`](../deploy/terraform/main.tf:30)).

## 4. Authenticate gcloud and Terraform

These are **two separate credential stores**, and conflating them is the most common
failure. `gcloud auth login` alone is not enough: the Terraform Google provider looks for
Application Default Credentials and fails with *"could not find default credentials"*
without the second command ([`deploy/README.md`](../deploy/README.md:58)).

```bash
# 1. Authenticate the gcloud CLI (interactive browser flow)
gcloud auth login

# 2. Authenticate Application Default Credentials (what Terraform reads)
gcloud auth application-default login

# 3. Point gcloud at the project
gcloud config set project raas-ocjs
gcloud config get-value project        # should print raas-ocjs
```

If you are on a headless machine, both `login` commands support
`--no-launch-browser` and will print a URL to open elsewhere.

## 5. Configure the deployment

All Terraform inputs live in [`variables.tf`](../deploy/terraform/variables.tf:5). The
overridable ones are documented in
[`terraform.tfvars.example`](../deploy/terraform/terraform.tfvars.example:1).

```bash
cd deploy/terraform
cp terraform.tfvars.example terraform.tfvars
```

Edit `terraform.tfvars` and set at minimum:

```hcl
project_id = "raas-ocjs"        # <-- the Project ID from step 3.2

region = "asia-south1"          # Mumbai; closest E2 region to a client in India
zone   = "asia-south1-a"

instance_name = "raas-judge"
machine_type  = "e2-standard-4"

boot_disk_size_gb = 30
low_tier_mb       = 256         # MUST stay 256 unless you intend a different tier

ssh_source_ranges   = []        # leave empty: SSH is already available over IAP
judge_source_ranges = []        # leave empty: the judge is reachable only over IAP
```

Optional overrides you may care about:

| Variable | Default | When to change it |
| --- | --- | --- |
| `region` / `zone` | `asia-south1` / `asia-south1-a` | To move closer to a different client. |
| `machine_type` | `e2-standard-4` | `e2-standard-2` for a smoke test; **never** a shared-core `e2-medium`/`small`/`micro`. |
| `boot_disk_size_gb` | `30` | 20 is workable but tight for the Rust build tree plus three images. |
| `low_tier_mb` | `256` | Leave at 256. The 128 MiB tier is documented as broken. |
| `repo_url` | `https://github.com/Hemanthkumar2k04/RAAS-OCJS.git` | If you deploy from your own fork, change it — it must be publicly clonable without credentials. |
| `repo_ref` | `main` | To deploy a branch or tag. |

> **Never commit `terraform.tfvars`.** It is already listed in
> [`deploy/terraform/.gitignore`](../deploy/terraform/.gitignore:9), and Terraform state
> is ignored too ([`deploy/terraform/.gitignore`](../deploy/terraform/.gitignore:4)).

## 6. Provision the VM with Terraform

From inside `deploy/terraform`:

```bash
terraform init          # downloads the hashicorp/google provider (~6.0)
terraform validate      # optional but cheap
terraform plan          # review: expect one VM, one VPC, one subnet, 2-4 firewalls
terraform apply         # type "yes" when prompted; takes about a minute
```

Terraform will create:

- a dedicated VPC and subnet (`10.10.0.0/24`),
- an IAP-only SSH firewall rule and an IAP-only judge rule (`tcp/3000` scoped to
  `35.235.240.0/20`),
- the VM, with a **metadata startup script** that runs the first-boot bootstrap.

The startup script is **preparation only**. It installs Docker, builds the three runtime
images, proves the cgroup mechanism, installs Rust, compiles the judge, and installs the
`raas-judge` systemd unit — **but deliberately does not start it**, so the judge can never
come up unauthenticated ([`startup.sh.tftpl`](../deploy/terraform/startup.sh.tftpl:174)).

Capture the outputs — every later step reads them:

```bash
terraform output                     # human-readable summary
terraform output -raw instance_name
terraform output -raw zone
terraform output -raw project_id
terraform output -raw tunnel_command
terraform output -raw ssh_command
```

## 7. Run the deploy script and verify

From the `deploy/` directory (one level up from `terraform/`):

```bash
cd ..                # now in deploy/
./deploy.sh
```

[`deploy.sh`](../deploy/deploy.sh:1) does six things, in order, and **exits non-zero if any
check fails**:

1. **Reads Terraform outputs** so there is one source of truth for instance, zone and
   project ([`deploy.sh`](../deploy/deploy.sh:27)).
2. **Waits for the first-boot bootstrap** to log `bootstrap complete`, polling every 20 s
   for up to 40 minutes. If the log contains `[FATAL]`, it aborts
   ([`deploy.sh`](../deploy/deploy.sh:44)).
3. **Preflight** — verifies the Docker cgroup driver, that the cgroup hierarchy is
   `cgroup2fs` (v2 unified), and that all three `judge-runtime` images exist
   ([`deploy.sh`](../deploy/deploy.sh:64)).
4. **Runs the cgroup probe** against a real container, writing `memory.high` and confirming
   the kernel increments the `high` pressure counter that reactive promotion waits on
   ([`deploy.sh`](../deploy/deploy.sh:92), [`cgroup_probe.sh`](../deploy/cgroup_probe.sh:1)).
5. **Generates the shared secret** — 32 random bytes as 64 hex chars — and installs it with
   mode `0600` to `/etc/raas/judge.env`, restarting the unit
   ([`deploy.sh`](../deploy/deploy.sh:100)).
6. **Verifies** that `/health` returns OK, that an unauthenticated `/submit` returns
   **HTTP 401**, and that a ~200 MiB submission is **promoted from Low to High**
   ([`deploy.sh`](../deploy/deploy.sh:109)).

The first boot takes **roughly 10–15 minutes** (Docker install, three image builds, Rust
compile). Subsequent runs are faster because each bootstrap step checks whether its work is
already done.

Expected final output resembles:

```
Summary
  cgroup driver   : systemd (must be systemd)
  cgroup v2       : cgroup2fs
  auth enforced   : yes (401 without token)
  promotion works : True
==> Deployment verified. The judge is running and promoting.
```

> If the bootstrap needs to be re-run **without recreating the VM** — for example after
> changing `repo_ref`, or because the first run was interrupted — use
> [`rerun_bootstrap.sh`](../deploy/rerun_bootstrap.sh:1):
> ```bash
> ./rerun_bootstrap.sh                # render, upload, run, follow the log
> ./rerun_bootstrap.sh --upload-only  # just stage the script on the VM
> ```

## 8. Access the running judge

`tcp/3000` has no public firewall rule by default, so the supported path is an **IAP
tunnel** that forwards your local port 3000 to the VM:

```bash
gcloud compute start-iap-tunnel raas-judge 3000 \
  --local-host-port=localhost:3000 \
  --zone=asia-south1-a \
  --project=raas-ocjs
```

Leave that running in its own terminal, then talk to `http://localhost:3000` with the
shared-secret header:

```bash
curl -s localhost:3000/health
# -> {"status":"OK"}

curl -s -X POST localhost:3000/submit \
  -H 'content-type: application/json' \
  -H "x-raas-token: ${RAAS_TOKEN}" \
  --data @submission.json
```

### Retrieve the token

The token was generated on the VM and never printed by `deploy.sh`. Read it back over IAP:

```bash
gcloud compute ssh raas-judge --zone=asia-south1-a --project=raas-ocjs \
  --tunnel-through-iap --command='sudo cat /etc/raas/judge.env'
```

Export it locally so the commands above work:

```bash
export RAAS_TOKEN=$(gcloud compute ssh raas-judge \
  --zone=asia-south1-a --project=raas-ocjs --tunnel-through-iap \
  --command='sudo cat /etc/raas/judge.env' | sed 's/RAAS_AUTH_TOKEN=//')
```

### Get an interactive shell

```bash
gcloud compute ssh raas-judge --zone=asia-south1-a --project=raas-ocjs \
  --tunnel-through-iap
```

### Follow the judge logs

```bash
sudo journalctl -u raas-judge -f
```

The single most important line to watch for is the **absence** of
`[moderator] failed to arm memory.high` — its presence means promotion is silently
disabled.

## 9. Run the benchmark experiment

The judge accepts `POST /submit`; the repository's harness is
[`benchmarks/raas_benchmark.py`](../benchmarks/raas_benchmark.py:1). The harness default
`JUDGE_URL` is a LAN address, so you **must override it**.

The cleanest arrangement is to run the harness **on the VM**, against `127.0.0.1:3000`,
so no wide-area latency contaminates the measured end-to-end times. SSH in first, then:

```bash
# On the VM
cd /opt/raas
python3 -m venv .benchvenv && . .benchvenv/bin/activate
pip install requests

# Back up the committed result CSVs first: the harness writes fixed filenames
cp -r benchmarks/results benchmarks/results.laptop-baseline

export JUDGE_URL=http://127.0.0.1:3000
export BENCH_SEED=42
export LIGHT_TIER_MB=256

# 1. Preflight — judge reachable, images present, cgroup v2 detected
python3 benchmarks/raas_benchmark.py preflight

# 2. Five verdict probes — proves AC/WA/RE/TLE/MLE paths all fire
python3 benchmarks/raas_benchmark.py probe

# 3. A short run before committing to the full corpus
python3 benchmarks/raas_benchmark.py run --limit 5
```

For the full scientific run, see
[`docs/GCP_DEPLOYMENT_PLAN.md`](GCP_DEPLOYMENT_PLAN.md:597) §8. The short version:

- **Stratum A** — the 100 committed CodeContests submissions × 4 strategies = 400 runs.
  These exercise correctness, routing and CFS accounting, but peak at ~53 MB, **far below
  the 179.2 MiB watermark**, so they produce **zero promotions**.
- **Stratum B** — the 6 synthetic heavy programs × 4 strategies = 24 runs. This is where
  **promotion actually fires** (expected: 8 promoting runs). Without stratum B you have
  spent cloud budget validating only the least controversial part of the system.

Pull the results and logs off the VM when finished:

```bash
gcloud compute scp --recurse --tunnel-through-iap \
  raas-judge:/opt/raas/benchmarks/results ./results-from-gcp \
  --zone=asia-south1-a --project=raas-ocjs

gcloud compute ssh raas-judge --zone=asia-south1-a --project=raas-ocjs \
  --tunnel-through-iap --command='sudo journalctl -u raas-judge --no-pager' \
  > raas-judge-server.log
```

## 10. Troubleshooting

### `memory.high` is never armed and promotion never fires

Run the probe directly on the VM — it tests the mechanism rather than inferring it from
config:

```bash
sudo /opt/raas/deploy/cgroup_probe.sh
```

The probe exits non-zero on failure. It distinguishes the three causes in order
([`cgroup_probe.sh`](../deploy/cgroup_probe.sh:36)):

- **cgroup v1** — `stat -fc %T /sys/fs/cgroup` must print `cgroup2fs`.
- **Not running as root** — writing `memory.high` as a non-root process returns `EACCES`.
  The systemd unit deliberately has no `User=` directive.
- **`memory.events` missing a `high` counter** — the memory controller is not enabled for
  that subtree.

### `Permission denied (os error 13)` on `/sys/fs/cgroup`

The service is not running as root. Confirm with
`systemctl cat raas-judge | grep User` (there should be none).

### Docker cgroup driver is `cgroupfs`, not `systemd`

Not fatal — the judge reads the real mount-relative path out of `/proc/<pid>/cgroup`, so it
resolves under either layout, with a four-way fallback
([`deploy/README.md`](../deploy/README.md:148)). Still worth fixing because `cgroupfs`
beside a booted systemd host is fragile. Check with:

```bash
docker info --format '{{.CgroupDriver}}'
cat /etc/docker/daemon.json    # expect "exec-opts": ["native.cgroupdriver=systemd"]
```

The bootstrap already pins this and **refuses to continue** if it did not take effect
([`startup.sh.tftpl`](../deploy/terraform/startup.sh.tftpl:67)).

### Quota errors during `terraform apply`

New projects often cap E2 vCPUs below 4. See [§3.4](#34-optional-verify-quota), or lower
`machine_type` to `e2-standard-2` for a smoke test.

### `deploy.sh` cannot find the instance

`terraform apply` must have succeeded first — the script reads all of its targets from
Terraform outputs ([`deploy/README.md`](../deploy/README.md:161)).

### Bootstrap never reports complete

Follow the log on the VM:

```bash
gcloud compute ssh raas-judge --zone=asia-south1-a --project=raas-ocjs \
  --tunnel-through-iap --command='sudo tail -f /var/log/raas-bootstrap.log'
```

Look for `[FATAL]` lines. Common causes: the cgroup probe failing, the Docker driver not
being `systemd`, or the repository URL not being publicly clonable.

### `start-iap-tunnel` fails with "failed to connect to backend (port 3000)"

The IAP firewall rule for `tcp/3000` is missing. Terraform creates it
([`main.tf`](../deploy/terraform/main.tf:86)); re-run `terraform apply` and confirm the
`raas-judge-allow-iap-judge` rule exists.

### `Address already in use` on port 3000

Another process holds the port on the VM:

```bash
sudo lsof -i :3000 && sudo kill -9 <PID>
sudo systemctl restart raas-judge
```

## 11. Cost management

Reference figures (verify before budgeting — provider prices change):

| Item | Approx. cost |
| --- | --- |
| `e2-standard-4` in `asia-south1` | ~`$0.161/hr` ex-GST, ~`$0.19/hr` with 18% GST |
| Three-hour run | roughly **Rs 55** |
| 30 GiB `pd-balanced` boot disk | ~Rs 3.5/month |
| **Left running 24/7** | ~**Rs 13,400/month** |

The last row is the one that matters. These are from
[`deploy/README.md`](../deploy/README.md:107).

Practical controls:

- Set a **billing budget and alert** (Console → Billing → Budgets & alerts) at, say, Rs 500.
- **Stop the judge when idle** but remember a stopped VM still bills for its boot disk —
  see [§12](#12-tear-down).
- **Destroy everything** when a benchmark campaign is finished.

## 12. Tear down

```bash
cd deploy/terraform
terraform destroy         # type "yes"
```

This removes the VM, the VPC, the subnet and the firewall rules. **Stopping the VM is not
enough** — a stopped instance keeps billing for its boot disk
([`deploy/README.md`](../deploy/README.md:118)).

Verify nothing is left behind:

```bash
gcloud compute instances list --project=raas-ocjs
gcloud compute disks list --project=raas-ocjs
```

## 13. Appendix — command cheat sheet

```bash
# --- One-time setup ---
gcloud auth login
gcloud auth application-default login
gcloud config set project raas-ocjs

# --- Deploy ---
cd deploy/terraform
cp terraform.tfvars.example terraform.tfvars      # then edit project_id
terraform init
terraform apply
cd ..
./deploy.sh

# --- Operate ---
terraform output -raw tunnel_command              # copy/paste to start the IAP tunnel
gcloud compute ssh raas-judge --zone=asia-south1-a --project=raas-ocjs --tunnel-through-iap
sudo journalctl -u raas-judge -f
sudo systemctl restart raas-judge

# --- Verify the mechanism on the VM ---
sudo /opt/raas/deploy/cgroup_probe.sh
stat -fc %T /sys/fs/cgroup                        # expect: cgroup2fs
docker info --format '{{.CgroupDriver}}'          # expect: systemd
docker images | grep judge-runtime                # expect: 3 images

# --- Re-run bootstrap without recreating the VM ---
cd deploy && ./rerun_bootstrap.sh

# --- Destroy ---
cd deploy/terraform && terraform destroy
```
